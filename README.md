# EventKit

A simple event organizer system for school and campus events. Create an event
once, then reuse its name, date, venue, and branding across badges, certificates,
posters, photo frames, and the participant page — with QR registration and
check-in.

> Built for a four-day development competition. The goal is a working, polished
> MVP and a reliable demo path, not a large platform.

## Stack

Next.js 16 (App Router, React 19, Server Components) · TypeScript · Tailwind CSS
v4 · shadcn/ui · Supabase (Postgres, Auth, Storage) · `qrcode` · `html5-qrcode` ·
jsPDF

## Start

```bash
cp .env.example .env.local     # fill in the four values (see docs/guides/setup.md)
npm install
npm run dev
```

You need a Supabase project. Apply the schema, then generate the types:

```bash
npm run db-push      # applies supabase/migrations to the hosted project
npm run db-types     # rewrites src/types/database.types.ts
```

Both talk to Postgres directly, so **Docker and a Supabase personal access
token are not needed**. `docs/guides/setup.md` has the full walkthrough,
including the one dashboard toggle that makes self sign-up work.

A local Docker stack is still available as an optional extra:
`make local-start`, `make local-reset`.

## Validate

```bash
npm run check                 # format:check + lint + typecheck + unit tests
npm run build
npm run test:e2e
npm run db-test               # pgTAP RLS suite against the hosted project
```

The live browser journey is opt-in because it writes to the real project:

```bash
E2E_LIVE=1 npx playwright test e2e/live-flow.spec.ts
```

## How it fits together

```text
src/
├── proxy.ts                  session refresh + optimistic route guard
├── app/
│   ├── (marketing)/          landing page and login shell
│   ├── (organizer)/          dashboard, event creation, event dashboard
├── components/ui/            shadcn primitives (owned code)
├── components/shared/        cross-feature UI
├── features/                 business code, one folder per concern
├── lib/                      supabase clients, auth routes, error contract, logger
└── config/                   validated environment, font names
```

Server Components are the default. Mutations are plain Server Actions that
validate with Zod, authenticate, authorize, call one service, revalidate, and
return a typed `ActionResult<T>`. Repositories are the only code that talks to
Supabase tables.

Start with `CONTEXT.md` for the decision record, then
`docs/architecture/overview.md`.

## Security notes

- Row Level Security is enabled on every table, with separate policies per
  command. Anonymous clients have **no** access to `participants` or
  `attendance`; the public pass page reads through a token-gated function.
- QR codes contain a 256-bit random token generated by the database — no
  personal data — and attendance is unique per participant per event, so a
  rescan can never create a second record.
- A certificate can only be issued to a participant who actually checked in. The
  rule is enforced by an RLS `WITH CHECK`, not only by the interface.
- `SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely. It is read only by the
  offline seed script, lives in `server-only` code, and must never reach a
  Client Component or a request path.

### Rotate your credentials

During setup the service-role key and the database password were pasted into a
chat session, so treat both as exposed. Rotate them in
Supabase → Project Settings → API Keys and → Database after the competition, and
keep `.env.local` out of version control.

Two known gaps, documented rather than hidden: anonymous registration is not
rate limited, and a participant pass link is a bearer secret (the page says so).
