# Authentication Flow

EventKit has one authenticated role: **organizer**. Participants never create an
account; they receive a private link to their own pass.

## Sign-in

- Email and password via Supabase Auth, PKCE flow, no third-party provider.
- `/login` is a Client Component that calls `supabase.auth.signInWithPassword`
  through `@supabase/ssr`, so the session lands in cookies immediately.
- `src/proxy.ts` refreshes those cookies on every request and makes an
  **optimistic** redirect: an unauthenticated visitor to an organizer route is
  sent to `/login?next=<path>` before rendering. This is a navigation
  convenience only.
- `/auth/callback` exchanges the PKCE code for a session. The `next` value is
  passed through `safeRedirectTarget`, which accepts only application-relative
  paths. Absolute URLs, protocol-relative URLs (`//evil.example`), backslash
  variants, and anything containing whitespace are rejected, so a crafted link
  cannot bounce a user off-site after sign-in.

## Session storage

Cookies written by `@supabase/ssr` are `HttpOnly` and `SameSite=Lax`, and
`Secure` in production. The refresh token never reaches client JavaScript.

| Concern                                | Owner                                                    |
| -------------------------------------- | -------------------------------------------------------- |
| Issuing, rotating, and revoking tokens | Supabase Auth                                            |
| Keeping cookies current                | `src/proxy.ts` on each request                           |
| Writing cookies from a Server Action   | `src/lib/supabase/server.ts`                             |
| Expiry and logout                      | Supabase Auth; logout clears cookies and calls `signOut` |

There is no custom session protocol, no second refresh path, and no client-side
trust in a session flag.

## Where authorization is actually enforced

The proxy is explicitly **not** a security boundary. Every one of these
re-verifies independently:

1. `src/app/(organizer)/layout.tsx` calls `getUser()` and redirects to `/login`
   if there is no session.
2. Every organizer Server Action calls `getUser()` and then checks that the
   event's `organizer_id` matches the authenticated user.
3. Every repository query filters by the authenticated user where the RLS policy
   alone would be ambiguous.
4. Row Level Security is the final backstop. A non-owner's `UPDATE` or `DELETE`
   silently matches zero rows; a statement with no policy for that command is
   refused with `42501`.

Server Actions are public endpoints. They treat their input as hostile, validate
with Zod, and return only the DTO the caller is entitled to — never a whole
database row.

## Participant identity

A participant is identified by a 256-bit random `qr_token`, generated by a column
default in the database so no client can choose it. The same token is the QR code
payload and the bearer secret for the participant's pass page:

```text
/events/[eventId]/participant/[participantId]?t=<qr_token>
```

`get_participant_pass(event_id, token)` returns that single participant's data
only when the token matches and belongs to that event, so a token cannot be
replayed against another event.

**Accepted limitation:** the pass URL is a bearer secret. Anyone holding the link
can view that participant's name, course, role, and check-in state. The page
carries a visible "do not share this link" notice, and the link is never emitted
in any public index or metadata.

## Check-in identity

A scan proves possession of the token, nothing more. `checkInByToken` looks the
participant up by `qr_token` **and** verifies `participant.event_id` matches the
event being checked in before writing attendance. Possessing a valid token for
event A grants nothing on event B.

## CSRF

Server Actions are invoked through Next's own action protocol, which requires the
framework's action ID and the `Next-Action` header and is not a plain cross-site
form post. Route handlers that mutate (`POST /api/uploads`) are authenticated by
cookie and must additionally be same-origin; the upload handler validates the
`Origin` header before reading the body.

## Known gaps

- **No rate limiting on anonymous registration.** There is no shared store in this
  deployment to count against, so a determined actor could submit many
  registrations. Mitigation for the competition is the per-event unique index on
  `student_id`, which stops duplicate identities but not volume. Add a rate limiter
  at the platform edge (Vercel firewall rule, Cloudflare, or a Supabase Edge
  Function with a KV counter) before any public deployment.
- **No email verification or password reset flow.** Organizer accounts are created
  manually for the demo.
- **No organizer invitations.** Any authenticated user may create events; there is
  one role by design.
